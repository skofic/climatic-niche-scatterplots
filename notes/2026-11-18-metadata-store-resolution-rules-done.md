## What changed in substance (§B)

- **`std_dataset_resolution_source`.** Definition: "The nominal pixel size, in metres, of the source data the dataset was built from, whatever the scope of its records." Description opens with the general meaning (every geographic dataset carries it; a grid beside the grid resolution, shape averages alone); the trust-for-a-small-shape paragraph is kept as the case of shape averages; the **coarsest-input sentence is removed** and rule 4 stands in its place ("One record, one resolution … 'the coarsest input' is not the resolution of any of them — it would make the reader believe all the data had it"; a compilation record carries no resolution, the reader goes to the source records); the ERA5-Land sentence stays as the general case of a latitude/longitude source, followed by "A grid in a projected coordinate system states its cell size directly: 1 km cells are `1000`."
- **`std_dataset_resolution_grid`.** Definition unchanged. "a dataset of shape averages carries … instead" became: a gridded dataset carries it **beside** the source resolution, the two say different things even when the grid was stored as published; shape averages carry the source resolution only. Rule 5 added as its own paragraph: "The property applies only when every cell of the grid has the same size in degrees. The unit is angular by choice: a cell's size in metres, and its area, change with latitude, while its angular size does not. A grid whose cells are a constant size in metres instead, such as 1 km cells in a projected coordinate system, is not a constant angle and carries the source resolution only." — Milko's wording to revise if he prefers.
- **`std_dataset_resolution`** (namespace): definition and description rewritten as the four numbered rules, then the records with nothing to state (non-geographic data, outlines, compilations — "there the reader goes to the source records"), then the projected-grid case.
- **`std_dataset_prop`**: the two bullets rewritten (source first: expected on every geographic dataset, absent on a table, outlines or a compilation, one record one resolution; grid: beside the source, only when every cell has the same size); **source now precedes grid** in `_fields` and `_recommended`. **`std_dataset_scope`**: the closing sentence now says every geographic dataset carries the source resolution and a grid the cell size as well. The manual page `datasets.dataset-record` carries rule 1, rule 2 and rule 4 in its properties paragraph.

## §C, §D

The three readings are what the texts now say: projected grids carry `std_dataset_resolution_source` only; non-geographic data, outlines and compilations carry neither; `EU-TREES4F_MAPS_2022` is yours to leave as one record without a resolution, and nothing in the dictionary contradicts it. Rule 1 stays `_recommended`: a requirement that depends on `std_dataset_domn.std_dataset_scope` from inside `std_dataset_prop` is not something a rule edge can express today (a rule amends the container it hangs off), so the rule lives in the texts and the manual, as the handoff proposed.

## §E — the rounding

The dictionary now states a convention, in `std_dataset_resolution_grid`'s description: **a fraction of a degree is written to ten decimals** (`0.0833333333`, `0.0416666667`, `0.0083333333` — the form of the term's own examples), "so that two records of the same grid state the same value". Ten decimals of a degree are about 0.01 mm on the ground, far below any grid's meaning, and the value stays a float with no display rounding declared. So of the two forms in the records today, keep `0.0833333333` and replace `0.08333333333333333`.
